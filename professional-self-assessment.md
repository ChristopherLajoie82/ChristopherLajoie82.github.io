The three-layered architecture that I have implemented for the Paint Tracking System shows that knowledge as well—I have a clear separation of concerns, clear responsibilities in each layer, and clear interfaces between layers that expose essential functionality and hide everything else. The software engineer with the least experience on a team should be able to work on their component without having to work through all the source code just to find where to plug in their own work.

## Data Structures and Algorithms

The Data Structures and Algorithms course, CS 260, provided a strong theoretical foundation in understanding algorithmic complexity, search and sort algorithms, and the trade-offs of choosing various data structures for different computational tasks. I was able to take some of those concepts and apply them in real code for Enhancement Two of this capstone. The core calculations of the PaintMixCalculator class have constant-time O(1) complexity. The algorithm for computing the breakdown of components needed to hit a particular total is efficient because it uses well-known paint mixing ratios (3:1:3 for interior jobs, 3:1:1 for exterior jobs) to directly compute the required quantities. This is where industry knowledge meets computer science, and by encoding that domain expertise into a working algorithm, I was able to produce something with genuine utility and computational efficiency.

Beyond the numerical calculations, I also made design decisions about data structures that meet the needs of the application. The job summary aggregation on the dashboard that displays the latest mixed job summary for a job number aggregates all the individual mixes from the underlying data structure, grouping by job number and showing calculated totals and the date range the mixes were performed. The dictionary structures returned by the calculator are also data structures designed to organize the breakdown of components in a way that is efficient to compute and easy for the UI layer to consume. These are a few examples of the data structure design decisions made in the capstone that reflect the algorithmic thinking encouraged in CS 260: choosing the right data structure for the problem and being aware of the trade-offs between computational complexity, performance, and practical usability in an actual application.

## Software Engineering and Databases

The software engineering practices and patterns I have learned in various classes along the way came together for Enhancement One of my capstone. I was able to refactor a 400-line monolithic script and turn it into a properly layered application, demonstrating clear use of the Repository pattern, a service-oriented architecture, and proper separation of concerns. The Data Access Layer, the Business Logic Layer, and the Presentation Layer are all well-defined and encapsulated their responsibilities. The DAL handles all the database code with parameterized queries to avoid SQL injection. The BLL handles validation and enforces business rules. The UI layer, migrated from Tkinter to PySide6/Qt6 for a more professional look, presents that data to the operator in a user-friendly way. It's not just theory because this architecture is the foundation of how large enterprise applications are designed because it makes the code maintainable, testable, and extensible by multiple developers working in parallel.

Database concepts from DAD 220 Introduction to SQL and CS 340 provided the theoretical understanding that I put into practice in Enhancement Three. The user authentication system is complete, from the properly normalized users table containing fields for the username, password hash, role, account status, failed attempt tracking, and lockout timestamps. Foreign key relationships from jobs to the users who created them enforce the audit trail. Indexes on columns that are frequently queried optimize performance. The Repository Factory pattern is implemented to make the app use SQLite for single-user deployments and PostgreSQL for multi-user network deployments, which are significant database architecture decisions that can affect a software product's scalability and range of use cases.

## Security

Security is something that I feel I have taken to heart. The concepts from CS 405 Secure Coding have stuck with me long after the semester is over. Thinking like an attacker is essential—considering every input as if it were malicious, every error message as a potential information leak, and every design decision as a possible vulnerability introduction. It is one thing to memorize the best practices, but a security mindset is something that has to be practiced and has to be on a professional developer's mind whenever they write code.

I tried to code securely every step of the way throughout all three enhancement milestones for this capstone. Every database query uses a parameterized statement to defend against SQL injection. Input validation is performed at multiple layers as a defense-in-depth measure. Error messages do not expose sensitive system details to end-users but still provide enough information to be useful and not leave them frustrated with the application.

The code for Enhancement Three, in particular, shows a more mature handling of security concerns and defensive programming practices. I used bcrypt to hash passwords with a work factor of 12, so a brute-force attack would be slow and computationally expensive. The account lockout logic bans users after 5 failed login attempts, locking them out for 15 minutes, to prevent automated password guessing attacks. Users are assigned roles to ensure they can only take actions that are appropriate for their role (database access is role-based). Even the password comparison is done in constant-time code to prevent a timing attack. This is not theory—this is how security works in production systems that have real people's sensitive data, such as Personally Identifiable Information, Stored Credit Card numbers, and Social Security Numbers.

## Summary: How the Artifacts Fit Together

The three individual enhancements within this capstone portfolio are not disparate projects, but rather different aspects of the same software system that have been layered on top of one another as the capstone project grew and matured. Enhancement One focused on Software Design and Engineering. It is where the foundations were laid with the architectural choices, including a three-layer application architecture, the Repository pattern, and the Service-Oriented architecture design decisions, that made the rest possible. Without that properly architected foundation, the additional features of Enhancements Two and Three would have been much harder and error-prone to add.

Enhancement Two was focused on algorithms and data structures. This is where the value-generating, core computational aspect of this system came in—the PaintMixCalculator object that encodes the domain expertise gained in 17 years of paint industry work into working algorithms. It is the algorithms that transform the basic computer into a tool for computational productivity.

Enhancement Three was focused on databases and completed the transformation of this system into a production-ready application with all the enterprise-ready security features, including bcrypt password authentication, account lockout protection, role-based access control, audit trails with foreign key relationships, multi-database support, and much more.
